● Your next layer is the services. They sit between the controllers (not written
  yet) and the two repositories you have. Here's what I'd put in them, based on
  your entities.

  Layout

  services/
    CategoryService.java
    ProductService.java
  exceptions/
    ResourceNotFoundException.java   -> 404
    DuplicateResourceException.java  -> 409
    GlobalExceptionHandler.java      (@RestControllerAdvice)
  dto/
    ProductRequest.java   (name, description, price, List<Long> categoryIds)

  CategoryService

  @Service
  @Transactional
  public class CategoryService {
      private final CategoryRepository categoryRepository;
      private final ProductRepository productRepository;

      public CategoryService(CategoryRepository c, ProductRepository p) { ... }

      @Transactional(readOnly = true)
      public List<Category> findAll() { return categoryRepository.findAll(); }

      @Transactional(readOnly = true)
      public Category findById(Long id) {
          return categoryRepository.findById(id)
              .orElseThrow(() -> new ResourceNotFoundException("Category " + id
  + " not found"));
      }

      public Category create(Category category) {
          if (categoryRepository.existsByNameIgnoreCase(category.getName()))
              throw new DuplicateResourceException("Category '" +
  category.getName() + "' already exists");
          return categoryRepository.save(category);
      }

      public Category update(Long id, Category input) {
          Category existing = findById(id);
          categoryRepository.findByNameIgnoreCase(input.getName())
              .filter(c -> !c.getId().equals(id))
              .ifPresent(c -> { throw new DuplicateResourceException(...); });
          existing.setName(input.getName());
          return existing;                       // dirty checking saves it
      }

      public void delete(Long id) {
          Category category = findById(id);
          for (Product p : productRepository.findByCategories_Id(id)) {
              p.getCategories().remove(category); // unlink from the owning side
  first
          }
          categoryRepository.delete(category);
      }
  }

  ProductService

  @Service
  @Transactional
  public class ProductService {
      // findAll, findById, search(name), findByCategory(categoryId), 
  findByPriceRange(min, max)

      public Product create(ProductRequest req) {
          Product p = new Product();
          apply(p, req);
          return productRepository.save(p);
      }

      public Product update(Long id, ProductRequest req) {
          Product p = findById(id);
          apply(p, req);
          return p;
      }

      private void apply(Product p, ProductRequest req) {
          p.setName(req.name());
          p.setDescription(req.description());
          p.setPrice(req.price());
          List<Category> cats =
  categoryRepository.findAllById(req.categoryIds());
          if (cats.size() != req.categoryIds().size())
              throw new ResourceNotFoundException("One or more categories not 
  found");
          p.setCategories(cats);
      }

      public void delete(Long id) { productRepository.delete(findById(id)); }
  }

  Why this design

  1. Business rules go in services, not controllers. The duplicate-name check,
     "category must exist", and unlinking before a delete are all rules. If they
     live in the service, every controller endpoint follows them, and you can
     test them without HTTP.
  2. Product owns the many-to-many link. Product has the @JoinTable, and
     Category.products is just mappedBy. Rows in product_category only change
     when product.getCategories() changes. That has two consequences:
     - Products get assigned to categories in ProductService, by passing
       category IDs.
     - Before deleting a category, CategoryService.delete has to remove it from
       each product's list. If it doesn't, MySQL rejects the delete because of
       the foreign key on the join table. That's why findByCategories_Id is
       useful here.
  3. @Transactional on the class. The unlink-then-delete steps happen as one
     unit, so a failure rolls everything back. Changes to loaded entities save
     automatically (dirty checking), so update doesn't need to call save. Lazy
     collections can be read safely while the transaction is open. readOnly = 
     true on reads is a small performance hint.
  4. Updates load the existing entity and copy fields onto it. The alternative,
     save(incomingObject), has two problems:
     - It would replace the product's categories with whatever the request sent,
       often an empty list.
     - It lets the client set id or timestamps.
  5. The request uses categoryIds, not whole Category objects. Clients send
     "categoryIds": [1, 3]. Accepting nested objects would let clients create or
     modify categories through the product endpoint.
  6. Services throw custom exceptions instead of returning null. One
     @RestControllerAdvice turns them into clean 404 and 409 responses, so
     controllers stay small. Each controller method is just one call to the
     service.
  7. Dependencies come in through the constructor, not @Autowired fields. The
     fields can be final, and unit tests can pass in mock repositories directly.

  One thing to watch: Product.categories is LAZY and not @JsonIgnored. Returning
  a Product from a controller only works because Spring's open-in-view setting
  is on by default, and it logs a warning about that. A cleaner fix is a
  ProductResponse DTO built inside the service.

  Small changes from the design I described:
  - Responses are DTOs too, not entities. They're built inside the service
    transaction, so the lazy categories list is always loaded before the
    response is sent.
  - Errors use Spring's standard ProblemDetail JSON. Failed validation returns
    400 with a map from each field to its error message.
  - Inputs are cleaned up. Names are trimmed, so " Books " and "books" count as
    duplicates, and repeated category IDs in a request are de-duplicated.
  - Updates write to the database immediately. Without that, the response would
    show the old updatedAt value.

  Two optional follow-ups:
  - You could add spring.jpa.open-in-view=false to application.properties. That
    turns off the open-in-view setting I mentioned last time, which these
    endpoints no longer need, and removes its startup warning.
  - README.md still says controllers aren't added yet, so that status line is
    out of date.

  To try it, start the app with mvnw.cmd spring-boot:run and open
  http://localhost:8080/swagger-ui.html.
