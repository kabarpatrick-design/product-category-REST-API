● ProductRepository: what it does and why

  repositories/ProductRepository.java:

  public interface ProductRepository extends JpaRepository<Product, Long> {
      List<Product> findByNameContainingIgnoreCase(String name);
      List<Product> findByCategories_Id(Long categoryId);
      List<Product> findByPriceBetween(BigDecimal min, BigDecimal max);
  }

  This interface is the data-access layer for Product. The services use it to
  read and write rows in the products table without writing any SQL or JDBC
  code.

  1. Why it's an interface with no implementation

  You never write a class that implements ProductRepository. When the app
  starts, Spring Data JPA finds any interface that extends JpaRepository. It
  then builds a proxy object that implements it and registers that object as a
  Spring bean. That's why ProductService can simply ask for one in its
  constructor and use it:

  productRepository.findAll();
  productRepository.save(product);

  Why do it this way? Almost every entity needs the same CRUD code. Spring
  generates it so you don't write the same boilerplate for every entity.

  2. JpaRepository<Product, Long>

  The two type parameters tell Spring:
  - Product: the entity this repository manages. It's mapped to the products
    table by @Entity/@Table in models/Product.java.
  - Long: the type of the primary key, which is private Long id in Product.

  Extending JpaRepository gives you these methods for free. Several are already
  used in ProductService:

  Why saveAndFlush for updates? updatedAt is set by the @PreUpdate hook in
  Product, and that hook only runs when JPA flushes changes to the database.
  Flushing right away means updatedAt is already filled in when the response DTO
  is built. CategoryService:63 has a comment explaining the same thing.

  3. The custom query methods ("derived queries")

  Spring reads each method name and turns it into a query. The pattern is findBy
  + property + keyword:

  findByNameContainingIgnoreCase(String name)

  - Name → the name field
  - Containing → LIKE %value%
  - IgnoreCase → compares in lowercase
  - SQL, roughly: SELECT * FROM products WHERE LOWER(name) LIKE LOWER('%phone%')
  - Why: it powers product search, so searching "PHONE" matches "iPhone 15"
    (ProductService:42).

  findByCategories_Id(Long categoryId)

  - Categories → the List<Category> categories field (@ManyToMany)
  - _Id → the id property of each category. The underscore makes it explicit
    that you're stepping into a nested property.
  - Spring generates a JOIN through the product_category join table:
  SELECT p.* FROM products p
  JOIN product_category pc ON p.id = pc.product_id
  WHERE pc.category_id = ?
  - Why, with two uses in CategoryService:
    a. CategoryService:41: lists all products in a category, e.g. GET 
       /categories/{id}/products.
    b. CategoryService:70: when you delete a category, this finds every product
       linked to it and removes the link first. Product owns the @JoinTable, so
       only the product side can delete rows from product_category. If you
       skipped this step, deleting the category would fail with a foreign-key
       error.

  findByPriceBetween(BigDecimal min, BigDecimal max)

  - SQL, roughly: WHERE price BETWEEN min AND max. Both ends are inclusive.
  - Why: it supports filtering by price range (ProductService:50). It uses
    BigDecimal to match the price field, because floating-point types like
    double cause rounding errors with money.

  4. Why use a repository at all (the architecture)

  Controller  →  Service  →  Repository  →  Database
  (HTTP/JSON)   (business rules)  (data access)   (SQL)

  - Separation of concerns: ProductController handles HTTP, ProductService
    handles rules (not-found checks, mapping to DTOs), and ProductRepository
    only talks to the database.
  - Testability: the service depends on an interface, so in unit tests you can
    replace it with a Mockito mock and skip the real database.
  - Swappable storage: you can change from H2 to MySQL to Postgres without
    touching the repository, because JPA/Hibernate generates SQL for whichever
    database you use.
  - Transactions: the repository's methods already run inside transactions. Your
    service's @Transactional methods group several repository calls into one
    transaction, as CategoryService.delete does.

  5. Things to watch out for

  - Spelling matters: if a method name refers to a field that doesn't exist
    (e.g. findByTitle), the app fails at startup. That's useful, because you
    find the mistake immediately.
  - Lazy loading: categories is FetchType.LAZY. If you read
    product.getCategories() outside a transaction, you'll get a
    LazyInitializationException. That's why the read methods in the services are
    marked @Transactional(readOnly = true).
  - When names get too long: for complex queries, use @Query instead of a very
    long method name:
  @Query("SELECT p FROM Product p WHERE p.price < :max ORDER BY p.price")
  List<Product> cheaperThan(@Param("max") BigDecimal max);

  CategoryRepository follows the same pattern. existsByNameIgnoreCase generates
  a cheap SELECT COUNT(...)-style check, which CategoryService uses to block
  duplicate category names.
