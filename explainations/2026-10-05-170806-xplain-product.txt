● The Product entity in models/Product.java is the Java class that maps to the
  products table. Each Product object is one row in that table, and
  JPA/Hibernate turns it into SQL for you.

  Class level

  @Entity
  @Table(name = "products")
  public class Product {
  - @Entity tells JPA that this class is stored in the database. Without it,
    ProductRepository extends JpaRepository<Product, Long> would fail when the
    app starts.
  - @Table(name = "products") sets the table name. Without it, the table would
    be named product.

  Fields

  id

  @Id
  @GeneratedValue(strategy = GenerationType.IDENTITY)
  private Long id;
  - @Id marks the primary key.
  - IDENTITY means the database creates the value with an auto-increment column.
    You never set id yourself; after save(), Hibernate reads back the value the
    database generated.
  - Why Long and not long: a new product that hasn't been saved has id == null.
    Spring Data uses that null to decide between INSERT (new) and UPDATE
    (existing).

  name

  @NotNull
  @Size(min = 2, max = 100)
  private String name;
  These are Bean Validation rules. Hibernate checks them before it writes to the
  database, so a blank or 500-character name throws an exception instead of
  being saved.

  description

  @NotNull
  @Size(min = 2, max = 1000)
  @Column(length = 1000)
  private String description;
  Why both @Size and @Column(length=…)? They do different jobs:
  - @Size is checked in Java at runtime.
  - @Column(length = 1000) sets the database column type. Without it the column
    defaults to VARCHAR(255), so a 600-character description would pass
    validation and then fail in the database.

  price

  @NotNull
  @DecimalMin("0.00")
  @Column(precision = 10, scale = 2)
  private BigDecimal price;
  - Why BigDecimal and not double: floating-point numbers can't store most
    decimal values exactly, so 0.1 + 0.2 gives 0.30000000000000004. Use
    BigDecimal for money.
  - precision = 10, scale = 2 creates a DECIMAL(10,2) column: up to 10 digits in
    total, with exactly 2 after the decimal point. The largest value is
    99,999,999.99.
  - @DecimalMin("0.00") blocks negative prices. A price of 0 (a free product) is
    allowed.

  Timestamps

  @Column(updatable = false)
  private Date createdAt;
  private Date updatedAt;

  @PrePersist  protected void onCreate() { this.createdAt = new Date(); }
  @PreUpdate   protected void onUpdate() { this.updatedAt = new Date(); }
  - @PrePersist runs once, just before the first INSERT.
  - @PreUpdate runs just before every UPDATE.
  - updatable = false leaves createdAt out of UPDATE statements. Even if code
    calls setCreatedAt(...) later, the database value never changes.
  - Why these are lifecycle callbacks: the timestamps are set automatically, so
    neither the service nor the client can forget them or fake them.

  The relationship with Category

  @ManyToMany(fetch = FetchType.LAZY)
  @JoinTable(name = "product_category",
          joinColumns = @JoinColumn(name = "product_id"),
          inverseJoinColumns = @JoinColumn(name = "category_id"))
  private List<Category> categories = new ArrayList<>();

  Many-to-many: one product can be in several categories (a laptop can be in
  "Electronics" and "Computers"), and one category holds many products. A single
  foreign-key column can't represent that, so a join table is used:

  products            product_category             category
  +----+--------+     +------------+-------------+  +----+-------------+
  | id | name   |     | product_id | category_id |  | id | name        |
  | 1  | Laptop | --> |     1      |      1      |->| 1  | Electronics |
  |    |        | --> |     1      |      2      |->| 2  | Computers   |
  +----+--------+     +------------+-------------+  +----+-------------+

  - @JoinTable names that table and its two columns.
  - Product is the owning side. Product has the @JoinTable, and Category says
    mappedBy = "categories". So changes to product.getCategories() are what get 
    saved. Adding a product to category.getProducts() alone does nothing in the
    database. This is why you link categories through the product, in
    ProductService.
  - FetchType.LAZY means categories aren't loaded from the database until you
    call getCategories(). Loading a list of 100 products doesn't also pull in
    every category.
  - = new ArrayList<>() starts the list empty instead of null, so
    product.getCategories().add(...) never throws a NullPointerException.

  On the other side, Category.products has @JsonIgnore. Without it, turning a
  category into JSON would include its products, each product would include its
  categories, and so on until a StackOverflowError. Your
  ProductResponse/CategoryResponse DTOs avoid this anyway, but @JsonIgnore is a
  safety net in case an entity is ever returned directly.

  Constructors and getters/setters

  - public Product() {}: JPA requires a no-argument constructor. Hibernate uses
    it to create the object, then fills in the fields when it reads a row.
  - The all-arguments constructor is a convenience for your own code, such as
    tests.
  - Getters/setters are used by Hibernate, Jackson and your service layer.
    Lombok's @Getter/@Setter would generate them for you, but writing them out
    is fine.

  Where it fits

  Client JSON → ProductRequest (DTO) → ProductService → Product (entity) → 
  ProductRepository → DB
  DB → Product → ProductResponse (DTO) → Client JSON
  Product is the shape of your data inside the app and the database. The DTOs
  are the shape the API exposes. Keeping them separate means you can change the
  table without breaking the API, and the reverse.

  Small things you could improve

  1. updatedAt stays null until the first update. Many projects set it in
     onCreate() as well, so new rows have a value.
  2. java.util.Date is the old date API. Instant or LocalDateTime, or
     Hibernate's @CreationTimestamp/@UpdateTimestamp, is the modern choice.
  3. public Product(){}; has an extra ;. It compiles, but you can remove it.
