● CategoryRepository: what it is and why it exists

  repositories/CategoryRepository.java:

  public interface CategoryRepository extends JpaRepository<Category, Long> {
      Optional<Category> findByNameIgnoreCase(String name);
      boolean existsByNameIgnoreCase(String name);
  }

  It's a short interface with no implementation class, and that's on purpose.

  What it is

  The repository is the layer that talks to the database for the Category
  entity. It's the only place the app reads or writes rows in the category
  table.

  You never write a class that implements this interface. When the app starts,
  Spring Data JPA builds the implementation for you and registers it as a bean.
  That's why CategoryService can receive one in its constructor
  (services/CategoryService.java:23).

  Part 1: extends JpaRepository<Category, Long>

  The two type parameters are:
  - Category: the entity this repository manages (the @Entity class in
    models/Category.java).
  - Long: the type of its @Id field (private Long id).

  By extending JpaRepository, you get a full set of CRUD methods without writing
  any code. Your project already uses several of them:

  Part 2: the two custom methods (derived queries)

  Optional<Category> findByNameIgnoreCase(String name);
  boolean existsByNameIgnoreCase(String name);

  These have no body either. Spring reads the method name and turns it into a
  query:

  - findBy + Name + IgnoreCase → SELECT * FROM category WHERE UPPER(name) = 
    UPPER(?)
  - existsBy + Name + IgnoreCase → SELECT COUNT(*) > 0 ... WHERE UPPER(name) = 
    UPPER(?)

  Name has to match a field in Category (private String name). If you misspell
  it, the app fails at startup instead of at runtime, which is useful.

  Why these two exist: they enforce the rule that category names must be unique,
  ignoring case. For example, "Electronics" and "electronics" can't both exist.

  - On create (CategoryService.java:46), existsByNameIgnoreCase is enough
    because you only need yes or no. It returns a boolean, so no entity gets
    loaded, which makes it cheaper.
  - On update (CategoryService.java:57), yes or no isn't enough. If you rename
    category 5 from "Books" to "BOOKS", the name already exists, but it belongs
    to the same category, so the rename should be allowed. That's why it uses
    findByNameIgnoreCase, which returns the matching category, and then
    .filter(other -> !other.getId().equals(id)) to throw only if the match is a
    different category.
  - Optional<Category> makes the "no match" case explicit, so you never get a
    null back.

  Why use a repository at all

  1. Separation of concerns. The controller handles HTTP, the service handles
     business rules (duplicate names, 404s), and the repository handles data
     access. The service never contains SQL.
  2. Less code. Basic CRUD plus two queries in 4 lines, instead of a
     hand-written DAO using EntityManager or JDBC.
  3. Testability. Because the service depends on an interface, you can mock
     CategoryRepository in unit tests.
  4. Swappable storage. The same code works with H2, MySQL or Postgres, because
     Hibernate generates SQL for whichever database you use.

  One thing to consider

  The uniqueness check only happens in Java. If two requests create "Books" at
  the same moment, both could pass existsByNameIgnoreCase before either one
  saves. A stronger fix is to also add a database constraint, @Column(unique = 
  true) on name. Even then, a plain unique index is case-sensitive in most
  databases, so you'd also need to store names in lowercase or use a
  case-insensitive collation.

❯ what is Optional for?                                                         

● Optional<T> is a container from Java 8 (java.util.Optional) that holds either 
  one value or nothing. You return it instead of null when "not found" is a
  normal, expected outcome.

  The problem it solves

  Suppose the method returned a plain Category:

  Category findByNameIgnoreCase(String name);  // returns null if not found

  Nothing in that signature tells the caller it might get null. If they forget
  to check, they get a NullPointerException at runtime:

  categoryRepository.findByNameIgnoreCase("Toys").getId();  // NPE if no "Toys"

  With Optional<Category>, the return type itself says "this might be empty". To
  reach the value you have to go through the Optional, so you deal with the
  empty case.

  How your code uses it

  1. getCategory (CategoryService.java:77): use the value or throw

  return categoryRepository.findById(id)
          .orElseThrow(() -> new ResourceNotFoundException("Category " + id + " 
  not found"));

  findById returns Optional<Category>. orElseThrow means: if a category is
  there, give it to me; if not, throw this exception. Your
  GlobalExceptionHandler then turns that exception into a 404.

  2. Update duplicate check (CategoryService.java:57): only act if a value is 
  present

  categoryRepository.findByNameIgnoreCase(name)
          .filter(other -> !other.getId().equals(id))   // keep it only if it's 
  a DIFFERENT category
          .ifPresent(other -> {                          // run only if 
  something is left
              throw new DuplicateResourceException(...);
          });

  Step by step:
  - No category has that name → empty Optional → filter and ifPresent do
    nothing.
  - The match is the same category being renamed → filter removes it → empty →
    nothing happens.
  - The match is a different category → it passes the filter → ifPresent throws.

  Without Optional, the same check looks like this:

  Category other = categoryRepository.findByNameIgnoreCase(name);
  if (other != null && !other.getId().equals(id)) {
      throw new DuplicateResourceException(...);
  }

  Common methods

  ┌───────────────────────┬─────────────────────────────────────────────────┐
  │        Method         │                  What it does                   │

  When to use it

  - Use it as a return type for "find one" lookups that may not find anything.
    Spring Data supports it directly.
  - Don't use it for fields, method parameters or collections. For collections,
    return an empty list instead (findAll() returns List, not Optional<List>).
